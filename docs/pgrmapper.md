# pgrmapper — read-only filtering proxy for PostgREST

`pgrmapper` is a FastAPI microservice that sits in front of PostgREST and
rewrites requests based on the caller's role. It exists for the cases pure
SQL/PostgREST cannot express — e.g. removing columns from responses
per-role at the HTTP layer.

It runs in its own container (`pgrmapper` service in compose) and is the
single backend of the nginx API gateway: host access goes
`host → gateway → pgrmapper → postgrest`. **The gateway↔pgrmapper hop is
mTLS**: pgrmapper serves TLS on port 8443 and requires a CA-signed client
certificate; nginx verifies pgrmapper's server certificate (against the same
CA) and presents the client certificate. The container runs the code baked
into the driver image — after editing `src/pgrmapper`, re-provision to
rebuild it. For debugging, run a live-edited plaintext copy inside the
driver:

```sh
pgrmapper        # listens on 0.0.0.0:8000 (PGREMAPPER_PORT) inside the driver
```

## What it does

1. **Validates GET routes against the database schema per request** — one
   effective `GET` route per table/view in `PGMAPPER_DB_SCHEMA` (plus `/`
   for the OpenAPI spec). Schemas applied after startup are served without a
   restart. Read-only: only GET requests are handled (other methods →
   `405`).
2. **Extracts the role from the JWT** — verified with `PGRST_JWT_SECRET`
   (HS256). No/invalid token → the anonymous role (`PGMAPPER_ANON_ROLE`,
   default `anon`).
3. **Looks up `(role, table)` in the access_filter table** — the internal
   table provisioned by `pgprovision access-filter` (schema
   `PGMAPPER_SCHEMA`, default `pgrmapper`). Roles/tables without a rule are
   forwarded unfiltered.
4. **Rewrites `?select=`** to the intersection of the requested columns and
   the visible columns: no `select` or `select=*` → the visible list; hidden
   columns are stripped; embedded resources pass through; an empty
   intersection → `403`. An empty `visible_columns` list blocks the table
   entirely (`403`).
5. **Forwards the request to PostgREST** with the Authorization header
   intact (PostgREST still enforces role membership, grants and RLS) and
   returns the response as-is.

## Configuration (defaults + environment overrides)

| Setting | Default | Environment variable |
|---|---|---|
| listen port | `8000` | `PGREMAPPER_PORT` |
| upstream PostgREST | `$POSTGREST_URL` or `http://postgrest:3000` | `PGMAPPER_UPSTREAM` |
| database URL | `$DATABASE_URL` or built from `POSTGRES_*` | `PGMAPPER_DB_URL` |
| exposed schema (routes) | `public` | `PGMAPPER_DB_SCHEMA` |
| access_filter schema | `pgrmapper` | `PGMAPPER_SCHEMA` |
| anonymous role | `anon` | `PGMAPPER_ANON_ROLE` |
| gateway public key (service JWT, RS256) | *(unset = gateway mode off)* | `PGMAPPER_GATEWAY_JWT_PUBLIC_KEY` |
| IdP JWKS URL (embedded user JWT) | *(unset)* | `PGMAPPER_IDP_JWKS_URL` |
| expected user-JWT audience | `myclient` | `PGMAPPER_IDP_AUDIENCE` |

## Health

`GET /health` returns `{"status": "ok"}` and exists for the container
healthcheck (an mTLS probe from inside the container). It is internal-only:
the nginx gateway returns 404 for `/health`, so it cannot be reached from
the host.

## Identity modes

- **Gateway mode (Apigee mimic)** — when the request carries the
  `X-User-Role` header: verify the service JWT (`Authorization`, RS256,
  gateway public key), verify the user JWT embedded in it against the IdP
  JWKS, then use the header role for the projections. Any failure → 401.
- **Legacy mode (driver debugging)** — no header: HS256 user JWT with
  `PGRST_JWT_SECRET` (role from the `role` claim), anonymous fallback.

See `docs/infra/apigee-mimic.md` for the full flow.

## mTLS

When `PGMAPPER_TLS_CERT` and `PGMAPPER_TLS_KEY` are set, the server speaks
TLS; `PGMAPPER_TLS_CA` additionally turns it into mutual TLS
(`ssl_cert_reqs=CERT_REQUIRED` — clients without a CA-signed certificate are
rejected). The compose service sets all three (port 8443, certs from
`certs/`).

The certificates are generated by `scripts/gen-certs.sh` (test CA,
`server.crt` with SAN `DNS:pgrmapper`, and the gateway's `client.crt`) into
gitignored `certs/`; `provision.sh` regenerates them when missing. The nginx
side is configured in `nginx/gateway.conf` (`proxy_ssl_verify on`,
`proxy_ssl_name pgrmapper`, client cert from `certs/`).

Verified behaviors:

- host → gateway → pgrmapper works only when both sides verify each other;
- direct HTTPS to `pgrmapper:8443` without a client cert → connection reset;
- with a client cert from a rogue CA → connection reset;
- with the CA-signed client cert → requests succeed.

## Example

With the todos example (columns `id, title, done, priority, due_date,
owner`) and rules `anon → [id, title]`, `editor → [id, title, done,
priority]`, `manager → all`:

```sh
# from the host, through the gateway (port from .env NGINX_PORT):
curl http://localhost:8080/todos                 # anon: id, title only
curl "http://localhost:8080/todos?select=*"      # same
curl "http://localhost:8080/todos?select=done"   # 403 (no visible columns)
TOKEN=$(scripts/jwt.sh --role manager --exp 1h)  # host-side JWT
curl -H "Authorization: Bearer $TOKEN" "http://localhost:8080/todos?select=*"
# manager: all six columns
```

Direct PostgREST access (from the driver) is unaffected: the proxy is the
only place filtering happens, which is exactly its purpose.

See [docs/pgprovision.md](pgprovision.md) for provisioning the
`access_filter` table.
